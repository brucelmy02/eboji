# e薄肌

此 Skill 随完整 eboji 项目使用。项目根目录是本文件所在目录的上两级；网页、动作库与服务端代码均需一起提供。保留用户在网页中使用卡片、3D 示范和训练记录的体验。

## 打开网页

- 按项目的 [README](../../README.md) 检查运行环境并启动服务。需要 Node.js 22+；无需安装第三方运行依赖。已运行的 eboji 服务可直接复用，使用实际启动端口打开网页。
- 预设、动作库、动画、组数标记和足迹不调用 AI。仅在用户请求 AI 计划或反馈分析时使用其本机已登录的 Codex；不要为了启动网页试跑一次 AI 生成。
- 用户资料、计划与反馈使用项目现有保存逻辑；卡组进度和足迹使用现有浏览器存储。不要把开发者的个人记录作为示例数据发给其他用户。

## 动作选择约束

首次生成计划、后续替换动作与训练建议都采用“库内优先，必要时例外”。

1. 以项目 [动作库](../../public/exercise-catalog.js) 为唯一的库内动作来源。先用用户器械、经验和运动条件筛选，再按目标组合合适动作。使用标准名称，避免不同变式混用卡片和动画。
2. 执行 [共用动作规则](../../lib/exercise-catalog.mjs) 中的 `createCatalogPrompt`；网页的计划生成与反馈分析已共享它。不要维护第二份独立动作清单或绕过现有筛选。
3. 库内能满足需求时，优先使用库内动作或调整合适动作的训练量。新鲜感、多样性、显得专业和模型偏好均不能作为新增库外动作的理由。
4. 只有库内没有合适替代、动作对具体需求确有必要、用户条件已确认适合时，才允许推荐库外动作。向用户说明具体必要性与库内无法替代的原因，并提供基础做法、支持物和“仅文字指导，暂无动画”的说明。不能用模糊的“更好”代替原因。
5. 不为满足库内优先而勉强安排不合适动作。信息不足时澄清，涉及疼痛或运动限制时遵循项目已有评估分支；库外例外不能绕过这些限制。
6. 调整计划时保留仍合适的原动作，仅对必要的新增或替换执行上述选择过程，不为提高库内占比改写整份计划。

保留现有 JSON 格式与历史记录。将上述规则交给已有计划生成和反馈流程执行；不要直接修改个人数据文件来伪造生成、反馈或训练完成结果。
